The whole thing in seven lines
  1. What. A YAML file describing a transformer becomes a HIP persistent megakernel: one launch decodes one token, all 36 layers plus the LM head and argmax inside it. §1, fig 1
  2. What that looks like in practice. 34 lines of YAML → 1674 lines of HIP in under a second → a model that did not exist an hour ago compiling at 0 register spills. Executed start to finish, failures included — including a three-week-old build break in a shipped config, sitting behind a green test, because a gate that checks self-consistency cannot detect a fault shared by both sides. §3, fig 3, fig 5
  3. Why it is faster. At batch size 1 the GEMMs are GEMVs, so kernel-launch boundaries and activation round-trips through HBM are the runtime. Fusing at two levels — registers and LDS — takes per-layer intermediate HBM traffic to zero. §4, fig 6
  4. Why it generalizes. Mirage's compiler emits call sites; its 50 433-line device library is hand-written, and its superoptimizer never mentions those kernels. So the assembling layer can be a static generator — and a new model becomes a table of shapes, not a search. §8, fig 10
  5. What it costs. No launch boundary means no free ordering, so Fleet MK builds its own: 35 device-wide barriers × 3.56 µs = 124.5 µs/token, sitting on a measured 3.50 µs hardware floor. §6, fig 8
  6. Where the time goes. MoE is ~40% of a layer. Inside one 13.4 µs tile: 0.88 µs of HBM wait, ~0.8 µs of math, and 3.65 µs just issuing loads. The phase is latency-bound, not bandwidth-bound. §7, fig 9
  7. The number, and the caveat. 2.921 ms/token through vLLM vs stock's 4.658 — 1.59× faster; also 0.78 ms behind Mirage's standalone driver. And GPT-OSS beats stock while Qwen3-8B is 1.63× slower, because the dense path never got this pipeline. Two architectures on opposite sides of stock is the finding. §12, fig 13

1. What Fleet MK is

Fleet MK is a code generator. Given a YAML description of a transformer, it emits a self-contained HIP persistent megakernel in which one GPU launch executes an entire decode step — all layers, the final RMSNorm, the LM head GEMM, and the argmax — for one token at batch size 1.

36
layers inside it (GPT-OSS)
240
workgroups (8 XCD × 30)
MXFP4
weights, fp8 activations
2.50 ms
standalone decode / token

Decode only. Prefill is compute-bound rather than latency-bound and stock kernels already handle it well; under vLLM it stays on the stock path.

The generator is the artifact, not the kernel

Everything under generated/ and the standalone driver are outputs. The regression gate is a byte-identity round-trip — run the generator in-process, compare against disk, all three architectures, sub-second, no GPU. Any kernel change must go through fleet_mk_generate.py or the round-trip goes red. It is the cheapest gate here and also the one with the sharpest limit — §3 shows a real bug it let through for three weeks, and why no stricter version of it would have helped.

python3 check_roundtrip.py     # kernel / launch / driver / build × {gptoss, qwen3, llama3}
Process hazard

Never run fleet_mk_generate.py without --output-dir. Its main() writes the driver and build script to the repo root, overwriting the live demo_gpt_oss_120b.py. Also, generated/ is gitignored — a git clean -xfd deletes every built .so and the dense artifacts.

2. The generator: one YAML, five artifacts

Five sections. model: and moe: are facts about the checkpoint, gpu: the target topology, build: compiler flags. measured: is the interesting one: search results, each annotated with the alternative tried and what it cost.

And then the one that gets cross-checked

The MoE phase's per-XCD tile count is derivable, so the measured: value is asserted against the derivation rather than trusted:

w13_tiles  = topk 4 × (5888 / 128)        = 184
w13_padded = pad_up(184, 240 workers)      = 240   ← 56 padding tiles, deliberately
w2_tiles   = topk 4 × (2944 / 64)         = 184
total      = pad_up(240 + 184, 8) / 8      =  53   == measured.moe_total_tiles_per_xcd ✓

Set w13_output_per_wg to 64 and this becomes 83; set w2_output_per_wg to 128 and it becomes 42. The assert fires on a stale YAML rather than letting a wrong tile count run — and the formula reproducing all three historical values is what makes it trustworthy.

Validation is where the bugs are caught

load_and_validate does three distinct kinds of check, and the distinction matters:

KindExampleWhat it protects
Structural — not tunable, each names its authority num_kv_heads == num_xcds; head_dim == 64 Mirage hardcodes kv_head_idx = xcd_id; the hd64 attention kernel static_asserts the head dim. Violating either is silent garbage.
Derived-vs-declared — compute it, then assert it agrees with the measured value moe_total_tiles_per_xcd, oproj_output_per_wg Keeps the auto-derivation honest without letting it silently override a measurement. The tile formula reproduces all three historical values (53 / 83 / 42).
Header cross-parse COUNTERS_PER_LAYER is parsed out of device_functions.cuh and asserted The generator once emitted 40 × 16 while the header said 103 × 16 — a 2.5× counter under-allocation that corrupts live barriers with no crash.

Facts that exist in more than one place get emitted from one definition

The most dangerous class of bug in this codebase is a constant that appears in two files and drifts. Three examples, all now single-sourced in the generator:

  • The pointer table. MIRAGE_IN_COUNT (24) and MIRAGE_OUT_COUNT (11) in the kernel, PTRS_PER_LAYER (36), and the 10368-entry table built in the driver (8 XCD × 36 layers × 36 slots) are four views of one fact. They are emitted from a single Python list. A mismatch here is not a crash — it is a pointer pointing at the wrong buffer.
  • The *_OPW tile widths. These control weight packing in the driver and GEMM tiling in the kernel. Change one file only and the output is garbage with no error.
  • The launch ABI. One Python parameter list produces both the emitted C signature and the ctypes argtypes. A ctypes list that is short or transposed is stack corruption, reproducible only under one of four env-var-selected decode paths.
The 23-parameter trap

Mirage's full-layer orchestrator takes 23 template parameters, every one int or bool. Transposing two compiles cleanly and produces wrong numbers. So they are emitted from a list of (name, value_expr) pairs — parameter order is data — with an assert on the list length. The emitted call is shown in full in §3.

What the generator writes: a specialization, not an implementation

Nothing in the layer body is an algorithm. The 850-line GPT-OSS kernel is 56 constants, six #includes, and a per-layer body that is one call — gang_full_layer_fused_kernel_mi300, 23 template parameters, five library symbols named in total. The exception is the 194-line LM-head GEMM and argmax tail, emitted inline because the vocabulary shard is the one tile shape that genuinely differs per model.

Every identifier in capitals is a static constexpr int emitted earlier in the same file and derived from the YAML — the table two subsections up. Nothing here was written by a person for this model. Three things are worth reading closely:

  • 23 template parameters, then 24 runtime arguments, and every one of the 47 is an int, bool, float, or pointer. That is the trap named in §2: transposing any two compiles without a diagnostic. The generator emits them from a list of (name, expr) pairs with assert len(...) == 23 and == 24 beside it, so the order is data that can be checked rather than 47 lines of hand-aligned text that an edit can permute.
  • /*SLIDING_WINDOW=*/0 is pinned, and the real window arrives as the last runtime argument. GPT-OSS alternates windowed and full attention by layer parity. Baking 128 into the template would instantiate the entire layer body a second time to vary one integer — 36 layers of code for one branch. The runtime override costs a register.
  • The /*NAME=*/ comments are on the template arguments and not on the runtime ones. The compiler checks neither; they exist because a template argument list is the thing a human actually has to read when the output is wrong.

The device-function library

This is where the performance lives, and it is deliberately not generated — a split that §8 argues is the interesting part of the whole system. Every quantity a model can change is already a template parameter. What is left to vary — MFMA scheduling, LDS layout, cache modifiers — are search results rather than derivations, and they live in the YAML measured: block.

Step 6 — Map the checkpoint, which is the actual work

The emitted driver is 686 lines and already handles pointer tables, MXFP4 quantization, padding, and the decode loop. What it cannot know is your checkpoint's attribute names. It emits the Llama-family convention:

layer = model.model.layers[li]
w_q = pad_weight_2d(layer.self_attn.q_proj.weight.data.to("cuda"), target_cols=HIDDEN_SIZE)
w_k = ...k_proj...   w_v = ...v_proj...   w_o = ...o_proj...
norm_w1_raw = layer.input_layernorm.weight.data
norm_w2_raw = layer.post_attention_layernorm.weight.data
w_gate = layer.mlp.gate_proj.weight.data     w_up = layer.mlp.up_proj.weight.data
w_down = layer.mlp.down_proj.weight.data
embed_weight = model.model.embed_tokens.weight.data

Mistral uses exactly these names, so here step 6 is zero work — the point of picking a Llama-shaped model. A model that names things differently (DeepSeek's MLA, a fused qkv_proj, tied embeddings) needs this block edited, and that edit is not generated. It is also not the interesting part: a rename, not a kernel change.

The layout the packing must satisfy is non-obvious, and the one place a mistake is silent. QKV is not concatenated Q, K, V — it is interleaved by KV group, so one workgroup's tile holds the heads it needs:

for g in range(NUM_KV_HEADS):            # 8 groups
    chunks.append(w_q[g*4*128 : (g+1)*4*128])   # 4 Q heads for this group
    chunks.append(w_k[g*128 : (g+1)*128])       # its K head
    chunks.append(w_v[g*128 : (g+1)*128])       # its V head
w_qkv = torch.cat(chunks, dim=0)                # (6144, 4096)
assert w_qkv.shape == (QKV_OUTPUT_SIZE, HIDDEN_SIZE)

Get the interleave wrong and nothing crashes: the GEMM is the right shape, the kernel runs at full speed, and the model emits fluent nonsense. The assert catches shape errors, not ordering errors — which is why the step-7 gate is an exact token id rather than a perplexity score.

A gate that checks self-consistency cannot detect a fault shared by both sides. 4. Two-level fusion — why it is fast

Fusion means computing two adjacent operators without letting the value between them reach memory. Everything below follows from one question: how far can the value travel before it must be written down? There are two answers, they are independent, and prior systems pick one.

Level 1
Register fusion. The consumer runs on the producer's accumulator while it is still in VGPRs. Scope: one GEMM plus its elementwise tail.
Level 2
LDS fusion. Consecutive GEMMs hand values to each other through LDS inside one persistent kernel. Scope: the whole model.

Level 1 removes the write; Level 2 removes the reason for the write, which is the kernel boundary. Doing both leaves zero intermediate HBM traffic per layer.

Level 1 — register fusion (GEMM epilogues)

Element-wise work is attached to the preceding GEMM and runs on the MFMA accumulator while it is still in VGPRs. The intermediate tensor is never materialized at all.

Worked example — SwiGLU with no intermediate, in registers only

W13 emits gate and up interleaved: W13_OUTPUT_SIZE = 5888 is 2 × 2944, gate in tile-iteration 0 and up in tile-iteration 1. The epilogue is called twice on the same wave and carries the gate across in four registers:

__device__ void operator()(f32x4_t acc, int wave_tile, ...) {
    bool is_gate = (wave_tile < 4);            // iter 0 = gate, iter 1 = up
    if (is_gate) {
        for (int i = 0; i < 4; i++)
            gate_save[i] = acc[i] + bias[abs_n];   // stays in a VGPR
    } else {
        for (int i = 0; i < 4; i++)
            out[..] = swiglu(gate_save[i], acc[i] + bias[abs_n]);
    }
}

gate_save[4] lives in the epilogue struct — entirely in registers. A conventional stack would have written 2944 f32 of gate to HBM, written 2944 of up, read both back, and written 2944 of product: four HBM passes over the intermediate, replaced by four VGPRs.

Level 2 — LDS fusion (persistent kernel phases)

A kernel launch is a memory-scope boundary: registers and LDS die at the end of it, so anything the next operator needs must be in HBM. That is why an operator-per-kernel stack pays for round-trips it does not logically need — the traffic is an artifact of the launch model, not of the math.

Fleet MK launches once per token. All 240 workgroups stay resident for all 36 layers, so LDS holds live values across phase and layer boundaries and the residual stream is the only thing that has to be written at all. The bill for this arrives in §6: a launch boundary is also a free device-wide barrier, and with one launch you have to build your own.

The last-layer ResAdd is parallel, deliberately

Mirage runs the final residual add on a single worker. Ported verbatim it cost ~1.1 ms/token, serializing 2944 elements through one workgroup. Fleet MK splits it across all 240 workers on disjoint column strides — safe precisely because they are disjoint: no worker reads a cache line another is zeroing.

Register pressure and the phase split

fleet_mk_phases.cuh exists to give the compiler register scopes: three __noinline__ functions (A: QKV+attention+merge, B: O-proj+TopK, C: MoE) let it reclaim registers between phases instead of holding every live range at once. The build lands at 226 VGPRs, 0 VGPR spills, 12 SGPR spills, 512 B LDS, 2 waves/SIMD. Any VGPR spill or a drop to 1 wave/SIMD is a hard fail regardless of what the clock says.

No launch boundary means no free ordering. Fleet MK has five primitives, and picking the cheapest correct one per site is most of the performance work.

The 3.5 µs floor

All three plausible device-wide mechanisms were microbenchmarked at 240 workgroups over 1000 iterations. A per-XCD release flag wins at 3.50 µs against a hierarchical barrier's 4.28 µs, and a flat global atomic is worse. That is a hardware floor, not an implementation defect — the inter-layer barrier measures 3.56 µs, essentially on it.

The barrier cannot simply be deleted

Removing the inter-layer barrier gives 2.008 ms/token — and garbage output. Layer n+1's QKV ResAdd reads workspace_f32 while layer n's MoE W2 is still accumulating into it via float atomicAdd. 35 barriers × 3.56 µs = 124.5 µs/token is real, but it buys correctness. It can be overlapped, not removed.

Heavier barriers are worse than the thing they fix

Strengthening the inter-layer sync with a heavier primitive pushed register pressure past the threshold, triggered SGPR spills, and cost 40%+. On this kernel barrier cost and register pressure are coupled: the correct move for a device-wide sync is the lightest primitive that is still correct.

Worked example — the QKV epoch barrier, and why nothing is ever reset

Two hard-won assembly-level lessons

LLVM serializes buffer_load ... lds. The compiler inserts s_waitcnt vmcnt(0) between every such intrinsic, turning 24 concurrent loads into a serial chain: 840 ns instead of 75 ns. Fix: a single inline-asm block issuing all 24. Worth −1.3% TPOT and a 70% cut in vmcnt stall time.

A global_load on an LDS pointer poisons the MFMA loop. In the O-proj GEMM the compiler converted a vmcnt(0) into lgkmcnt(1), producing 636K stall cycles for 8 MFMAs. The MoE W13 loop, hand-written in asm with lgkmcnt(4), runs at 1.01× theoretical. Same hardware, same operation count.

Working rule

Never guess at performance. After every kernel change, disassemble, verify the compiler emitted the intended pattern, and compare register counts against baseline. Several of the largest wins here were invisible in the source and obvious in the assembly.

8. The device-function library: why a static generator can support any model

§4 explained why Fleet MK is fast. This section is about why it generalizes — and the two answers are unrelated. Fleet MK is not a faster Mirage. It is what becomes possible once you notice what Mirage's compiler is actually compiling.

The problem: the compiler does not write the kernels

Mirage (MPK) is a persistent-kernel compiler with a superoptimizer. The advertised pipeline is a search over algebraic rewrites, a transpiler, and generated code. That is true of the graph. It is not true of the code that runs on the SIMDs. Three measurements on this tree:

  • The device kernels are hand-written C++. tasks/mi300/ is 60 files, 26 505 lines of hand-tuned HIP — MFMA mainloops, CK-FMHA split-KV attention, the fused MoE kernel (1 806 lines by itself). Across all five architectures the task library is 137 files, 50 433 lines. None of it is generated.
  • The superoptimizer has never seen it. src/search/ — 32 files, 6 598 lines — contains zero occurrences of MI300 and zero of gang. The search space and the fast kernels do not intersect. The fused path is reached only through 102 hand-written register_task call sites in persistent_kernel.py.
  • What the compiler emits is a call, not a body. Every registration in task_register.cc ends the same way: build an argument list, name a symbol, return the string.

The generated file is a dispatch switch over 117 task types (55 of them MI300) whose arms are those strings. 81 distinct kernel:: symbols are named this way, and the compiler writes the body of none of them. 8 066 lines of codegen produce parameter substitution and a switch; 50 433 lines of kernels are typed by a person.

Fleet MK's generated kernel reaches the same library the same way — emitted from a Python f-string rather than a C++ string-builder, but naming a symbol from the same header set. Its whole per-layer body is the worked example in §3: 23 template parameters, 24 runtime arguments, and not one line of algorithm. Two independent generators, written in different languages by different people, converge on the same output shape — because that is the only output shape the library admits.

The observation everything below rests on

If the compiler's device-level output is a template instantiation and an argument list, then the compiler is not the part doing the work — the library is. And an argument list does not need a superoptimizer to produce it. It needs a table of shapes.

Why the dynamic machinery can be dropped at batch size 1

Mirage's scheduler exists to resolve a dependency DAG whose shape is unknown until runtime. For decode at batch size 1, it is known at generate time:

  • The token count is 1. No ragged batch, no prefill mix, no data-dependent tile counts — the whole work decomposition is a function of the config.
  • The layer sequence is a straight line. 36 identical layers, no data-dependent control flow. The DAG has no branches to schedule around.
  • Every tile bound is derivable. moe_total_tiles_per_xcd, total_qkv_tiles_per_xcd, oproj_tiles_per_xcd — all computed by load_and_validate and asserted against the emitted header (§2).

So the 8 scheduler workgroups and the 301-entry task graph are solving a problem with no unknowns in it. Fleet MK deletes them and pays a different bill instead: 35 explicit device-wide barriers at 3.56 µs. That is the entire trade, and it is quantified below.

What Fleet MK replaces, precisely

Fleet MK calls Mirage's device-level sub-kernels — six headers, reached through -I<mirage>/include/mirage/persistent_kernel and nothing more elaborate than an include path. What it replaces is the layer above: how work is scheduled and synchronized across the whole model.

The consequence: adding a model becomes a table, not a search

Once the fast code is a library of templates and the generator's job is to instantiate them, supporting a new model stops being a compilation problem. Every axis a transformer varies along is already a template parameter or a constant:

Mistral-7B's ten mechanical minutes and its 60-line diff against Llama3-8B were not evidence that the generator is clever. They are evidence that the performance was already in the library, and the new model simply inherited it.

Why this, and not the 1.59×, is the interesting claim

Mirage demonstrated that a megakernel beats an operator-per-kernel stack. Fleet MK's contribution is orthogonal: the megakernel's performance lives in a device-function library, not in the compiler that assembles it — so the assembling layer can be a static generator, and the library becomes a reusable asset across models and across frameworks. One library now serves a dense and an MoE architecture, a standalone driver and a vLLM backend, from four YAML files.

The honest limit of the static approach: it cannot invent a kernel it does not have. Three cases where the dynamic machinery is the right answer —

  • Batch > 1 with ragged sequences. Tile counts become data-dependent and a runtime scheduler earns its keep. Fleet MK's decomposition is frozen at generate time.
  • A tile shape nobody has written. MLA, a new quantization format, head_dim ≠ 64 on the MoE path. Fleet MK rejects these at validate time with an assert naming a file and a line (§3) — and Mirage would fail too, since the library is shared. The constraint is the library's, not the generator's.
  • Fusion decisions that depend on a checkpoint's values, not its shape. Nothing in Fleet MK's pipeline is value-dependent, so this has not arisen — but it is where a search would find something a table cannot.

Which points at the research direction this section makes visible. If the library is the asset, the compiler's real job is generating library entries, not scheduling calls to them. Neither system does that today: Mirage's superoptimizer searches a graph whose leaves are hand-written, and Fleet MK's generator instantiates those same leaves. Closing the gap — a compiler that emits the MFMA mainloop, the LDS staging, and the cache-modifier choice rather than selecting among human-written ones — is the open problem both systems are standing next to.

An older gap analysis, and what happened to it

docs/fleet_mk_vs_mirage_perf_gap.md recorded Fleet MK at 8.08 ms against Mirage's 2.19 ms, enumerated 5.09 ms of gap, and predicted ~3.0 ms post-fix. Actual: 2.50 ms — beaten, because adopting Mirage's fused layer body wholesale collapsed several line items at once rather than fixing each phase separately. 9. vLLM integration

A fast kernel that only runs in a benchmark script is not a serving backend. The integration makes Fleet MK's megakernel the decode path of a real vLLM engine — continuous batching, paged KV, the full sampler, the OpenAI-compatible API — while prefill stays stock.

Discovery: a general plugin, not a fork

vLLM exposes a vllm.general_plugins entry point. At engine startup it calls register(), which swaps each stock model class for a Fleet MK subclass:

def register():
    from vllm import ModelRegistry
    from .model import FleetMKQwen3ForCausalLM, _make_gptoss_class
    ModelRegistry.register_model("Qwen3ForCausalLM", FleetMKQwen3ForCausalLM)
    try:   # separate vLLM module; may be absent in older builds
        ModelRegistry.register_model("GptOssForCausalLM", _make_gptoss_class())
    except Exception as e:
        log.info("fleet_mk: GptOssForCausalLM not registered (%s); dense path unaffected.", e)

Registering both is harmless: vLLM instantiates whichever architecture the checkpoint declares. Enable with VLLM_PLUGINS=fleet_mk; the stock baseline is VLLM_PLUGINS= (empty). No vLLM source is modified.

Three seams, and nothing else

The subclasses are thin. Everything model-agnostic lives in FleetMKModelMixin, parameterized by a ModelSpec. The mixin overrides exactly three methods:

compute_logits() After a Fleet MK MoE decode, returns the bf16 logit row the megakernel already computed (§11); otherwise falls through to stock.

MRO matters: the mixin is listed first (class T(FleetMKModelMixin, StockModel)) so its overrides win while super() still reaches the stock implementation.

10. Zero-copy KV

The problem

Attention needs every past token's K and V, and vLLM owns a paged KV cache — here roughly 184 GiB — in its own layout. Fleet MK's kernel originally read and wrote its own K/V buffers, so a per-request gather-copy reshuffled vLLM's prefill KV before decode could start: two full KV stores plus a per-request copy.

The trick

Rather than converting between layouts, force a vLLM attention backend whose physical KV layout is already byte-identical to Fleet MK's, then alias the pointers.

The aiter backends allocate KV as (2, num_blocks, block_size, num_kv_heads, head_size) — the leading 2 makes K and V each contiguous — and write it through reshape_and_cache_flash, the non-reordered layout. Reshaped, that is bit-for-bit Fleet MK's flat [entries, num_kv_heads × head_dim] buffer. (vLLM's default Triton/ROCm backends reorder K or interleave the leading 2 — incompatible with a single flat pointer.)

kvc = attn.kv_cache[0]                          # [2, num_blocks, block_size, n_kv, head]
k_alias = kvc[0].reshape(entries, n_kv * head)  # a view, not a copy
v_alias = kvc[1].reshape(entries, n_kv * head)
assert k_alias.data_ptr() == kvc[0].data_ptr()  # zero-copy invariant guard
buffers.set_kv_aliases(k_aliases, v_aliases)    # fleet_mk's K/V now point at vLLM's pool

Binding is lazy, on the first decode, because vLLM allocates the KV cache after load_weights(). Fleet MK's page-indirection array kv_indices is then driven straight from vLLM's block_table: during decode the megakernel appends the new K/V into vLLM's block and reads all prior KV in place.

Why PAGE_SIZE is 128

BackendLimiting mechanismblock_size cap
rocm_aiter_fa (MHA) paged_attention_v1 → static_assert(BLOCK_SIZE <= k_thread_per_block), which is 32 ≤ 32
rocm_aiter_unified_attn (Triton) LDS use = block_size × 1024 B against the 160 KB cap ≤ 160
vLLM itselfBlockSize = Literal[1, 8, 16, 32, 64, 128, 256]≤ 256

So the kernel's original PAGE_SIZE = 4096 could never bind; 128 is the largest power of two under the unified backend's LDS budget. Measured cost is negative — 2.501 → 2.491 ms/tok on GPT-OSS, 6.798 → 6.768 on Qwen3, identical registers and output — because PAGE_SIZE only feeds address arithmetic and seqlen_k. It also buys coverage: at 4096 the demos' ~150-token runs fit in page 0, so cross-page addressing was never exercised.

Hybrid KV cache must be disabled for GPT-OSS

vLLM's hybrid KV-cache manager overlays GPT-OSS's two attention types on shared physical memory with separate per-group block tables; Fleet MK's decode uses ONE block table for all layers. disable_hybrid_kv_cache_manager=True unifies every layer to FullAttentionSpec. Fleet MK's kernel still applies the sliding-window mask itself, so only the KV-memory saving is lost. No-op for uniform models such as Qwen3.

Three asserts guard the scheme and fail loud rather than producing garbage tokens: the backend must be an aiter flash backend, block_size must equal PAGE_SIZE, and the reshape must be a view (data_ptr equality) rather than a silent copy.

11. Fused logits: deleting vLLM's redundant LM head

This is the clearest example of an optimization that only becomes visible once the kernel is inside a real serving stack.

The megakernel's argmax epilogue computes sum + bias for every vocab entry and discards all but the maximum. Fine for the standalone driver, which only wants the argmax. But vLLM's sampler needs the full logit row — and it was getting it by running its own bf16 lm_head, recomputing exactly what the megakernel had just thrown away.

GptConfig gained an optional logits_output. Null — the standalone default — keeps the argmax-only tail. Non-null makes the epilogue also store the bf16 row:

float val = sum + bv;
long long abs_idx = (long long)(partition_start + out_n);

if (logits_out != nullptr) {

if (val > thread_max) { ... }

Three details carry most of the correctness argument:

  • A null check, not an #ifdef. One compiled .so serves both drivers; the standalone path pays only a predicated branch.
  • The stored value is the same val the argmax compares, at the same absolute vocab index — so the fused row cannot disagree with Fleet MK's own greedy pick.
  • compute_logits() consumes its flag rather than just reading it. Prefill, dummy runs, and stock-path fallbacks fall through to vLLM's lm_head. Silently returning a stale row on those paths would be wrong output with no error.

12. Performance, stated honestly

Read this before quoting any number

enforce_eager disables hipGraph capture, and it is not neutral between the two sides. Stock vLLM's decode is a long tail of small kernel launches, so graph capture is most of its performance; Fleet MK's decode is ONE launch with almost nothing to gain. Eager mode therefore flatters Fleet MK by a large factor.

An earlier revision reported GPT-OSS as 8.3× faster than stock. That was an artifact: the benchmark hardcoded enforce_eager=True. Stock GPT-OSS with graphs is 4.658 ms/token, not 26.113 — a 5.6× swing belonging entirely to the baseline. Always state which capture mode a number came from.

Method

Prefill-cancelling: time greedy generate() for a short and a long output of the same prompt and difference out the identical prefill.

ms/token = 1000 × (T_long − T_short) / (N_long − N_short)     # 8 vs 128 tokens, best of 3

Two traps this method and the profiler share: vLLM v1 runs the engine in a subprocess (profiling needs VLLM_ENABLE_V1_MULTIPROCESSING=0), and key_averages() lists the CPU launcher op alongside its kernel with both carrying device time — naive summing double-counts.

  • GPT-OSS through vLLM: token ids [200005, 35644, 200008, 976, 1825, 10648, 261, 5678] — identical to the standalone driver. First token 35644 ('analysis') is the standing correctness gate. Output is coherent prose with the correct channel structure.

Divergence position is not a corruption signal

Fleet MK runs MXFP4 weights and fp8 activations against stock's bf16, so logits differ slightly and a near-tie eventually resolves the other way. Expected, not a defect — corruption looks like a re-emitted prefill token, doubled words, or a degenerate repeat, not a fluent synonym 14 tokens in. MoE W2 also accumulates 4 experts with float atomicAdd, so bit-reproducibility is a bonus, not a gate.

13. Open items and known-dead directions

Open: Fleet MK cannot be hipGraph-captured

File "fleet_megakernel_vllm/mixin.py", line 180, in forward
    cur_pos = int(positions[0].item())
torch.AcceleratorError: HIP error: operation not permitted when stream is capturing

.item() is a device-to-host sync, which HIP forbids inside a capture region. There are two such syncs, and removing them is more than deleting the .item():

  • cur_pos drives host-side control flow: num_pages_used = (cur_pos + page_size) // page_size sizes a dynamic-length slice of kv_indices. A captured graph freezes whatever length it recorded.
  • token_id is a by-value launch argument, so a captured graph would decode the same token forever — a plausible degenerate repeat, not a clean error.

The token_id half is already solved in the kernel ABI and merely unused by the plugin: GptConfig carries cur_token_ptr alongside cur_token_id, and the kernel does int cur_token = config.cur_token_ptr ? *config.cur_token_ptr : config.cur_token_id; — a device-side read, which is capture-safe. The plugin passes nullptr today. cur_pos is the harder half and needs the page-count arithmetic moved on-device.

Bound the payoff before doing the work

With FLEET_MK_PROFILE=1 the megakernel's own GPU time is ~2.38 ms against 2.921 ms end-to-end, so everything host-side — scheduler, sampler, launch, round-trip — is ~0.54 ms/token. That is the ceiling on what capture could recover, and capture would take only part of it. It was ~0.83 ms before the fused-logits change took a bite out of it.

Open: the dense pipeline

Qwen3 is 1.63× slower than stock because it still runs the multi-barrier dense kernel. Porting the fused single-barrier pipeline to it is the change that would close this. The fused-logits trick does not apply — the dense kernel has no logits_output in its ABI — and would not close the gap anyway.

Two levers remain on GPT-OSS, and neither reaches 2.1 through vLLM

  1. hipGraph capture — ceiling 0.54 ms, realistically a fraction of it.
  2. Overlapping the inter-layer barrier — 124.5 µs, and it cannot be deleted outright (§6).

Silent-corruption hazards, collected

  • The three *_OPW constants control weight packing in the driver and GEMM tiling in the kernel. Change one file only → garbage, no crash.
  • All 23 Mirage template parameters are int/bool. Transposing two compiles cleanly.
  • COUNTERS_PER_LAYER: 40 vs the real 103 is a 2.5× under-allocation that corrupts live barriers.

  • A ctypes argtypes list that is short or transposed is stack corruption reproducible only under one of four env-selected decode paths.
